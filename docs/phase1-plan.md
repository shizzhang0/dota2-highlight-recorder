# 阶段 1 计划：命令行 MVP

目标：**一条命令录完一场比赛里某个玩家的全部高光**。每个高光输出一个视频，可选拼成合集。

技术验证的结论见 [`docs/spikes/`](spikes/)。

## 已定的决定

| 事项 | 决定 | 依据 |
|---|---|---|
| 录制方式 | Dota 2 回放自带的视频剪辑工具；OBS 作为备选 | [验证 6](spikes/06-clip-builder.md) |
| 片段规则 | 按每次击杀实际的开打时间动态定起点，默认值见下 | 里程碑 1 统计程序：本地 17 场录像、1036 次击杀 |
| 分辨率 | 默认跟游戏窗口一致；可以指定（启动游戏时带 `-w` `-h`） | 参照 CS2 参考项目 |
| Dota 以普通模式开着 | 先提示，用户同意后再重启游戏 | — |
| 合集 | 放在阶段 1 做（`--compile`） | 拼接导出段本来就要用 ffmpeg |
| 录像不在本地 | 阶段 1 提示用户先在游戏里下载；按比赛 ID 从 OpenDota 下载作为里程碑 3 的可选项 | 不碰游戏目录，最省事 |

### 片段规则

1. **每次击杀生成一段**：从"这波战斗开打前 2 秒"到"击杀后 3 秒"。
   - **开打时间（推荐口径）**：从击杀那一刻往回看**击杀者与任意敌方英雄之间**的伤害记录，双向都算（被杀者先出手也算开打）。召唤物、幻象、熊、守卫等附属单位造成的伤害记给主人；打在幻象身上的伤害、塔/小兵/野怪造成的伤害不算。相邻两次伤害间隔不超过阈值的算同一波战斗，取最早的一次。
   - 理由：镜头跟的是击杀者，画面里的"开打"就是击杀者第一次和敌方英雄交手。团战里先打 B 再收掉 A 的情况，只看"击杀者 ↔ 被杀者"会漏掉前半段；而初步统计用的"被杀者 ↔ 任意敌方"口径，在队友追了很久、我们的玩家最后补刀时，片段开头镜头里是我们的玩家在别处。
   - 起点有上限（最多往前看多少秒）和下限 3 秒；找不到相关伤害时（例如塔杀被记给了我们的玩家）就用下限。
2. **合并成片段**：同一玩家相邻两次击杀间隔不超过 18 秒，放进同一个片段。这和 Dota 判定多杀的窗口一致，游戏播报的双杀、三杀一定在同一个片段里。
3. **片段内的空档**：同一片段里相邻两段之间的空档，**不超过 N 秒就保留**（连成一段），超过才剪掉。
   - 每剪一次空档就要多导出一次，固定开销（切前台、点界面、确认对话框、等文件）估计 15–20 秒；保留空档只多渲染约 1.8 × N 秒。两者在 N ≈ 10 秒时持平，而且短空档剪掉会造成跳切。
4. **超过 56 秒的部分**拆成多次导出再拼接，因为剪辑工具单次导出不能超过约 60 秒。导出时选区两头各多留 1 秒（见录制流程第 6 步），所以单次导出最长 58 秒，仍保留 2 秒安全余量。优先在空档处拆；如果只能在连续画面中间拆，拆分点会有 ±1 秒的重复或缺口（把手和 GSI 都只精确到秒，流复制拼接没法修正），作为已知限制。旧规则（固定前 8 秒、后 3 秒）下本地片段最长约 33 秒；新规则起点最多往前 20 秒、短空档也保留，片段会更长，超过 56 秒的情况有多少要等里程碑 1 的统计结果，再决定这条要不要多花功夫。
5. **所有数值都是参数**，规则函数接收一个参数结构体，命令行可以修改。

**选定的默认值**（2026-10-22，用户根据里程碑 1 统计程序 `crates/clips/examples/stats.rs` 的结果选定）：

| 参数 | 默认值 | 依据（本地 17 场、1036 次击杀） |
|---|---|---|
| 开打口径 | (c) 击杀者 ↔ 任意敌方 | 镜头跟着击杀者；(b) 中位数只有 3.7 秒，团战前半段会丢 |
| 同一波战斗的伤害间隔 | 3 秒 | 5 秒会把两波相隔不远的战斗连在一起 |
| 起点上限 | 19 秒 | (c) 3 秒口径下开打 → 击杀的 90% 分位是 16.6 秒，再加开打前 2 秒 |
| 空档保留阈值 N | 8 秒 | N 取 5 / 8 / 12 时导出次数只在 877–898 之间变化，影响很小 |

按默认值切出 877 个片段，其中 129 个两杀以上；时长中位数 10.6 秒、90% 在 22 秒以内、最长 37.6 秒；没有超过 56 秒的片段。录完一名玩家一整场预计中位数 3.6 分钟、90% 在 7.4 分钟以内（不含启动游戏）。

对比：固定前留白 3 秒（CS2 的默认值）在口径 (a) 下只能完整拍到 12% 的战斗，8 秒只有 48%。

## 录制流程

```text
d2hr record <比赛ID> [--player 序号或账号] [--clips 1,3] [--compile] [--resolution 1920x1080]
  1. 解析录像：玩家、击杀、多杀、连杀、伤害记录、时钟 ↔ tick 换算
     录像不在本地 → 提示用户先在游戏里下载这场录像，退出
  2. 按片段规则生成计划：片段 → 导出段；打印预计耗时
  3. 准备游戏：
     ├─ Steam 没登录 → 提示
     ├─ 清掉上次可能残留的 GSI 配置，写入我们自己的 GSI 配置（独立端口，录完删除）
     ├─ Dota 没开 → 带 -netconport -insecure（以及 -w -h）启动
     ├─ Dota 以普通模式开着 → 提示，同意后重启
     └─ Dota 已经带 -insecure 开着，但收不到我们的 GSI 包
        （GSI 配置只在启动时读取：上次没清干净，或用户自己带参数启动）→ 同样提示重启
  4. 设置守护：记下原值 → 关掉边缘接管、把剪辑工具的输出目录改到临时目录、
     把 dota_clip_builder_max_duration 设成 120（时间轴窗口变成 120 秒，选区落在中间，
     离窗口边缘远，把手不容易被夹住；精度 9.1 像素/秒仍然够）
     → 结束时一定恢复（正常结束、出错、Ctrl+C 都要恢复），并删除我们的 GSI 配置
  5. 只加载一次录像（重新加载会把镜头重置成自由视角）
     → 菜单设好英雄追踪 + 本方迷雾 → 数字键选人，GSI 确认
  6. 每个导出段：
     跳到这段的中点 → 打开剪辑工具 → 按时间轴窗口换算，拖动两个把手（两头各多留 1 秒）→ 导出
     → 等文件写完（大小 > 0 且稳定）→ 关掉"导出成功"提示
     → 核对：直接读 mp4 里 moov/mvhd 记录的实际时长（毫秒级，不需要 ffprobe），和计划长度比；
       再看导出期间 GSI 的起止时钟（约一秒一包，本身有 1 秒误差）确认位置没错。
       只有文件 0 字节、时长偏差超过 2 秒或起点位置不对，才微调把手重新导出
     → 每次点击前后都截一张窗口图（游戏在前台，直接截屏幕上窗口所在区域）。出错时把截图和日志一起存进输出目录，方便排查；
       成功就丢掉
  7. ffmpeg 拼接同一片段的导出段（流复制，不重新编码）→ 改名 → 放进输出目录；可选拼成合集
  8. 恢复所有设置，关掉剪辑工具，把前台还给用户（可选关闭游戏）
```

**从第 5 步开始到录完，用户全程不能动鼠标键盘**：每段导出都要切到前台点界面，中间是渲染，一场比赛可能要十来分钟。命令行开始前会倒计时提示，`d2hr plan` 也会提前打印预计耗时（导出总秒数 × 1.8，加上每段的固定开销）。

文件名：`比赛ID_玩家序号_英雄_起点_终点[_多杀].mp4`，例如 `9046032624_2_juggernaut_04-00_04-20_双杀.mp4`。

### GSI 配置（2026-10-22 定）

- **自己维护，不用第三方库**：Rust 里只有 dota-gsi，功能远超所需（类型化模型、事件推导），却不写配置、不认 token；我们只读 4 个字段。也暂不和 dota2-game-helper2 抽共享库，两边只有约 300 行管道代码重叠，到阶段 2 做 Tauri 时再考虑。
- **从 helper2 移植**（注明出处）：`gsi.rs` 的请求体大小上限和 `auth.token` 校验（没带 auth 段的放行并只警告一次，带了但不对的丢弃。本机 helper2 也在收 GSI，两份配置都会生效，所以必须认 token）；`gsicfg.rs` 写、删配置的写法（内容相同不重写，只删自己那个文件）；`dotacfg.rs` 读设置文件和找账号目录（已移植到 `game::steam`）。
- **配置文件** `game\dota\cfg\gamestate_integration\gamestate_integration_d2hr.cfg`，录完删除，启动时先清掉残留：
  - `uri` 为 `http://127.0.0.1:2122/`，`timeout` 5.0，`buffer` 0.1，`throttle` 0.1，**`heartbeat` 1.0**（回放暂停时状态不变，没有心跳就收不到包，等确认时会误判超时）；
  - `data` 只开 `map` 和 `hero`（用到 `map.clock_time / paused / matchid / game_state` 和 `hero.teamN.playerK.selected_unit`），不要 `provider`、`player`、`items` 等；
  - `auth.token` 用固定字符串 `d2hr`：配置只在游戏启动时读取，每次随机就意味着"游戏已开着"时永远得重启。
- **端口 2122**：紧挨 netcon 的 2121；在 Windows 临时端口范围（49152–65535）之外，避开 Steam 的 27015–27050 和 helper2 的 53000。可用 `--gsi-port` 覆盖；启动时先探测能不能绑定，被占用就报错提示换端口，不悄悄换（换了配置就得重启游戏）。

## 里程碑（各提一个 PR）

1. **不用开游戏的部分**
   - `replay` 补伤害记录和本地录像列表。
   - **解析失败时给出明确提示**：读录像头里的游戏版本号（`build_num`），和代码里记录的"解析器验证过的版本号"常量对比；录像更新时提示"这场录像的格式比较新，请更新软件"，而不是直接抛出底层错误。
   - **解析完做合理性检查**：10 名玩家、击杀数不为 0、时钟采样单调递增。格式变化不一定报错，验证 5 里 `m_fGameTime` 消失就是悄无声息的；检查不通过时同样给出上面的提示。
   - `clips` 实现片段规则，以及统计程序 `crates/clips/examples/stats.rs`：对三种开打口径、两档伤害间隔、N = 5 / 8 / 12 秒，在本地全部录像上算出开打 → 击杀的分布、片段数和时长、导出次数、预计总耗时，以及超过 56 秒的片段数和其中需要在连续画面中间拆分的次数。统计程序直接调用正式的规则函数，以后调参数可以复现。
   - 统计程序顺带把本地录像和 OpenDota 的击杀、死亡对账结果存成一个小数据文件（`crates/clips/examples/data/`），以后升级解析库做回归时不用联网。文件里只存比赛 ID 和每个位置的击杀、死亡数，**不存玩家昵称和账号**。
   - **把对比结果拿给用户选定默认值**，然后再写 `d2hr list` 和 `d2hr plan`（打印片段、导出段和预计耗时）。
   - 同时把 README 的原则改成"除临时的 GSI 配置外，不修改游戏文件"。
2. **游戏自动化**
   - 一开始先测：运行时改 `dota_clip_builder_output_folder` 是否立即生效、输出目录里 clipN 从几开始编号；游戏在后台时（`snd_mute_losefocus`）导出的视频有没有声音，以及渲染期间游戏是否必须一直在前台；120 秒窗口下导出 58 秒的选区能否成功（验证 6 只测过 120 秒窗口导出 36 秒）。
   - 设置守护、自己的 GSI 配置、镜头和迷雾设置、剪辑工具导出一段并自动核对。
   - 点击前后自动截图，出错时连同日志保存（见录制流程第 6 步）。
3. **`d2hr record` 全流程**：ffmpeg 拼接、命名、合集、指定分辨率。用用户最近的一场比赛实测。可选：录像不在本地时按比赛 ID 从 OpenDota 下载（前提是先测 `playdemo` 能不能读 replays 目录以外的文件）。
4. **稳健性**：按锚点换算的坐标在**一个 16:9 分辨率**下实测（用户屏幕是 16:10）、独占全屏、用户改过热键、中途出错和 Ctrl+C 时的恢复。

不新增单元测试，每个里程碑都靠实际运行来验证。

## 解析库的升级策略

- `Cargo.lock` 锁定 source2-demo 的版本，不跟着每次发布升级。
- **必须升级的情况**：Dota 更新改了录像格式，新录像解析失败或数据不对。其他情况（修了我们碰到的 bug、加了需要的功能）按需升级。
- 升级步骤：`cargo update -p source2-demo` → 用本地全部录像做回归检查（击杀、死亡数和保存好的对账数据比对，时钟换算误差）→ **更新代码里"解析器验证过的版本号"常量** → 通过后提交。0.6 这类大版本要手动改版本号，可能要改代码。
- 做桌面应用时加自动更新（参照 dota2-game-helper2 的 Tauri 更新插件），解析器升级后用户能及时拿到。

## 需要用户准备

- Steam 已登录，装好 Dota 2，要录的比赛已在游戏里下载录像。
- ffmpeg：阶段 1 是命令行，先要求放在 PATH 里或用 `--ffmpeg` 指定路径；做成桌面应用时再随软件一起打包。
- **录制开始后全程不要动鼠标键盘**，`d2hr plan` 会提前告诉你大概要多久。
